## Findings

- Routing reversal is not data rollback. Reversion now requires a compatible and current old system or a tested reconciliation/recovery path.
- Replaced unconditional zero-downtime, instant rollback, harmless shadow execution, and backward-compatible-at-every-step claims with explicit prerequisites.
- Dual writes are not universally impossible without distributed transactions: outbox/CDC supports asynchronous propagation, with ordering and idempotency requirements, not atomic cross-store commits.
- Removed unsupported generic calendar estimates and fixed numerical test-surface claims. Durations now identify workload-specific measurement or rollout gates; risk labels remain editorial judgments.
- Replaced the Parallel Run citation to Parallel Change, which describes interface evolution rather than shadow execution. Removed blanket claims about schema-registry portability, mandatory database-first extraction, managed services requiring the most rework, and stateful workloads belonging on VMs.

## Uncertainty And Gaps

- Source verification is documentary, not a tested migration. Connector/engine versions, reverse-conversion feasibility, RPO/RTO, business invariants, and failure recovery must be rehearsed for each deployment. Dynamic `stable`/`latest` docs can change; PostgreSQL evidence is pinned to 18 and Vitess evidence to archived 22.0. No claim is made that 22.0 is the newest Vitess release.
- Native PostgreSQL logical replication and Debezium are distinct mechanisms. Neither the PostgreSQL object restrictions nor one connector's delivery behavior are asserted for every CDC product. Log retention loss can require resnapshotting; a current-state snapshot does not reconstruct all historical events.
- The RabbitMQ guide verifies RabbitMQ-to-RabbitMQ procedures, not RabbitMQ-to-Kafka offset/schema mapping. Cross-product acknowledgements, ordering, duplicates, schema IDs, and replay must be tested separately; the old universal portability assertions were removed, not replaced with invented guarantees.
- The RabbitMQ page contains inconsistent direction wording in its federation/shovel narrative versus examples. No configuration or direction-specific command was copied; implementation requires checking the installed version's federation reference.
- API headers communicate lifecycle information, not client migration completion. Generic cloud and Kubernetes rollback advice is synthesis; IAM/secrets migration, egress budgets, storage-driver portability, backup restore drills, and service-specific reverse migration remain deployment-level work.
- Fetch follow-up: Google URLs redirected to `docs.cloud.google.com`, and API versioning then redirected to AIP-185; all final sources were fetched successfully. The attempted Vitess `/docs/22.0/user-guides/migration/resharding/` returned 404 and is not used as evidence. Its configuration-advanced guide and archived reference succeeded.
